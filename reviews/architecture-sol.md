# Architecture review — current application

Reviewer: Codex peer agent `/root/sol_lessons_13_24` (GPT-5.6 Sol, high). Date: 2026-09-18. Scope: current `core.js`, `app.js`, `sw.js`, `serve.py`, and `tests/core.test.cjs`. Legacy archive was excluded. This review made no code changes. Node was not available in this shell, so findings are from exact control and data-flow inspection rather than an executed JavaScript reproduction.

## Remaining concrete failures

1. **High — import merge can silently discard written lesson work.** `app.js:18` creates `lessonWork.L01` with empty fields as soon as L01 is viewed. `core.js:122` merges `lessonWork` only if the entire lesson key is absent. If a user opens L01 on a new device and then merges a backup with completed L01 fields, `completedLessons` is unioned but the imported L01 fields are discarded. The page can show L01 complete while its written answers are missing. The same top-level-key rule discards incoming `reviews`, `templates`, and `sessions` values on conflict; imported archived `legacy.reviews` are not merged at all. Preserve distinct field values or make conflicts visible and recoverable. Current tests only assert that a conflicting current draft wins; they do not cover an empty current shell against a populated imported draft.
2. **High — cross-tab protection is bypassed by import.** Ordinary `persist()` refuses to save once the `storage` event marks a tab stale (`app.js:22–25, 296`). The merge/replace click handler (`app.js:286–290`) calls `C.backup` and `C.save` directly with the tab's old in-memory `state`. A stale tab can therefore overwrite a newer save from another tab despite the visible warning. Reread current storage or block import until the tab is refreshed, then base merge on the latest state. Event timing still leaves a small simultaneous-write race for ordinary edits because `localStorage` provides no transaction across tabs.
3. **High — release changes can remain invisible indefinitely.** `sw.js:2–17` caches assets first under a fixed cache name and returns cached responses even when online. If a pack, `app.js`, or `core.js` changes while `sw.js` bytes and `CACHE` stay the same, `reg.update()` finds no new worker and existing clients keep old content. The root maintainer has acknowledged a planned release ID from hashes of served assets; this finding remains open until implemented and verified.
4. **Medium — a new practice session destroys a resumable old draft.** `startPractice()` overwrites `state.sessions.quiz` without checking for an unfinished session (`app.js:114–120`). A learner can enter draft answers in one lesson, navigate to another lesson and press “Практиковаться”; the first session's `draftAnswers` and response list disappear. Submitted attempts survive, but the first session cannot be resumed. Offer resume or an explicit replacement path, or preserve multiple sessions.
5. **Medium — readiness may score the wrong first attempt after merge.** `core.js:150–154` takes the first array entry for each scenario family. `mergeState()` concatenates current attempts before imported attempts (`core.js:119–121`) without ordering by `answeredAt`. If an imported earlier correct answer follows a current later wrong answer, the displayed “first attempt” is wrong; the reverse can inflate readiness. Choose the chronological earliest attempt per family with a deterministic tie rule.
6. **Medium — resumed answered question can display the wrong key after a content update.** `quizPage()` loads the current question by ID and calls `feedback(q,a)` (`app.js:133–153`), even though `a.questionSnapshot` records the exact version answered. If options or keys change under the same ID, reload can show a saved result with the new correct answer and explanation. The summary correctly uses the snapshot (`app.js:156–161`); active-session feedback should also use it, and an unsubmitted question with a changed version needs an explicit restart or migration decision.
7. **Medium — quota can block recovery of a damaged save.** Recovery first writes a second full copy of the corrupted primary blob to a new localStorage key, then saves the selected valid backup (`app.js:322–330`). Near quota, that extra write throws, so even a smaller backup cannot be restored through the UI. The user can download raw data, but there is no quota-safe restore path. Make the downloaded raw file the preservation step or use a bounded fallback that does not require doubling storage.
8. **Medium — confirmed future/invalid training inflates the 35-hour indicator.** The training form stores any date and `validateState()` checks title, hours and confirmed but not `date` (`app.js:226`, `core.js:83`). `experiencePage()` totals every confirmed training entry (`app.js:179–185`). A future-dated or malformed imported course can raise the displayed count before completion. Validate date and completion status against today, then exclude ineligible entries from the count.
9. **Low — a timed answer can be accepted after the deadline.** The interval handler and `quizPage()` mark a session finished on deadline (`app.js:129–132, 212`), but `submitAnswer()` does not check `remainingSeconds()` before recording (`app.js:238–245`). A backgrounded tab can have an expired wall-clock deadline while its interval is throttled; submitting before the next tick records a late answer and can alter the timed-session result. Check deadline in the submit handler.

## Maintainer resolution after review — 2026-09-18

The findings above describe the pre-fix revision. Before publication the maintainer applied these changes:

1. Merge fills missing or empty lesson fields while preserving nonempty current answers, merges revealed sections and legacy review records, and keeps the earlier review due date. Different unfinished imported sessions remain resumable. Deterministic regression test added.
2. Import now refuses to write from a tab marked stale. Browser regression checks replacement cannot overwrite another tab's newer profile. localStorage still has no transactional compare-and-swap for precisely simultaneous writes.
3. tools/release.py derives the cache version from served resources, with normalized line endings; verify.py fails if resources and cache ID disagree. CI checks before deploying.
4. Starting another practice session parks the unfinished session; the practice page can resume it. Browser regression preserves typed numeric draft through topic changes.
5. Readiness orders attempts by answeredAt and stable ID before selecting first-family results. Regression covers earlier imported wrong and hinted attempts.
6. New sessions retain question snapshots; active feedback uses the answered snapshot, and unanswered session items retain the selected version.
7. Recovery permits restoring after downloading the raw original when insufficient quota prevents a second local copy.
8. Training dates are checked; only confirmed, valid dates completed by today contribute to the total. Regression added.
9. submitAnswer checks deadline again before accepting an answer and ignores duplicate submission for an already answered index.

These are maintainer resolutions, not a claim that the Sol reviewer reran the corrected build. Executed checks are recorded in TESTING.md.

The primary attempt and `responseIds` are mutated together before one synchronous `C.save` on normal submit, so an ordinary successful save should restore them together. `load()` returns a recovery state rather than silently resetting a corrupted primary save. `serve.py` serves application files from loopback; no issue in its permitted routes was found within this review's data-loss/scoring/offline scope.
